Anatomía de una URL

Cada vez que escribes una dirección en el navegador, o haces clic en un enlace, en realidad estás usando una URL (Uniform Resource Locator, "localizador uniforme de recursos"). No es un texto suelto: tiene partes fijas, cada una con su función, igual que una dirección postal tiene calle, número y ciudad en un orden concreto.

Vas a ver cada parte por separado.

Protocolo

http:// o https:// indican el "idioma" con el que el navegador y el servidor se van a hablar. La s de https significa "seguro": la información viaja cifrada, para que nadie que intercepte la conexión por el camino pueda leerla. Hoy en día casi todas las páginas usan https; los navegadores modernos avisan con un icono de advertencia cuando una web todavía usa http a secas.

Dominio

Ya lo viste en la sesión 1: el nombre que el DNS traduce a una IP (iesramonllull.net). A veces va precedido de un subdominio como www. o blog., que identifica una parte concreta dentro de ese mismo dominio — piensa en ello como distintos departamentos de un mismo edificio, todos con la misma dirección postal pero un despacho distinto.

Ruta (path)

Todo lo que viene después del dominio y antes de ? o #. Indica qué recurso concreto pides dentro de ese servidor: puede ser un archivo real (/imagenes/logo.png) o, en webs más modernas, una sección organizada por carpetas aunque no exista un archivo físico con ese nombre exacto (/blog/posts).

Parámetros (query string)

Empiezan con ? y son pares clave=valor separados por &. Sirven para pedirle al servidor una variación concreta de la misma página, sin necesitar una ruta distinta para cada combinación posible.

🤔 Antes de seguir: si un buscador de tienda online tiene la URL tienda.com/zapatillas?color=azul&talla=42, ¿qué está pidiendo el usuario, con sus propias palabras?
Ver respuestaEstá pidiendo ver la página de "zapatillas", pero filtrada solo por las que son de color azul y de la talla 42.

Fragmento (ancla)

Empieza con # y va al final de todo. A diferencia de las demás partes, el fragmento no se envía al servidor: lo gestiona solo el navegador, para saltar directamente a un punto concreto dentro de la misma página (por ejemplo, un apartado con ese id). Es exactamente lo mismo que usa el índice "En esta página" de esta propia web.

Recuerda: el id ya lo usaste antes como destino de un enlace de ancla y luego como selector CSS. Aquí es el mismo id otra vez, esta vez señalado desde una URL completa en vez de desde un <a href="#seccion"> dentro de la misma página.

Cómo se carga una página: petición y respuesta

En la sesión 1 viste el esquema básico: el cliente pide, el servidor responde. Ahora que sabes leer una URL completa, puedes ver ese intercambio con más detalle: es una conversación con un formato fijo, llamada HTTP (HyperText Transfer Protocol).

Cada petición lleva un método, que dice qué tipo de acción se está pidiendo. Los dos más conocidos:

MétodoPara qué se usa
GETPedir un recurso: cargar una página, hacer clic en un enlace, escribir una dirección. Es lo que has usado siempre hasta ahora.
POSTEnviar datos al servidor (por ejemplo, un formulario). Este curso no vais a crear formularios, pero conviene saber que existe.

Cuando navegas de página en página o abres imágenes, prácticamente siempre estás usando GET: nunca se lo tienes que indicar tú a mano, el navegador lo hace solo.

Códigos de estado

En la sesión 3 ya viste dos códigos en la pestaña Network: 200 (todo correcto) y 404 (no encontrado). Son parte de un sistema más amplio: la respuesta del servidor siempre incluye un número de tres cifras que resume qué ha pasado, antes incluso de mirar el contenido.

Código Significado Ejemplo real
200 OK — todo ha ido bien La página se carga con normalidad
301 Redirección permanente Escribes http:// y el servidor te reenvía solo a https://
404 No encontrado Escribes mal el nombre de un archivo o de una ruta
500 Error interno del servidor El servidor ha recibido la petición, pero algo se ha roto al intentar responder

Fíjate en la diferencia entre 404 y 500: el 404 significa que el servidor sí ha respondido, pero diciendo "esto no existe aquí"; el 500 significa que el servidor tenía que responder algo, pero se ha encontrado con un fallo propio al intentarlo. El problema, en el primer caso, casi siempre está en la URL que has pedido; en el segundo, está en el propio servidor.

🤔 Antes de seguir: si publicas tu web y mueves sin querer una imagen a otra carpeta sin actualizar el <img src="...">, ¿qué código de estado esperarías ver para esa imagen, y de quién sería "el fallo": del servidor o de cómo está escrito tu HTML?
Ver respuestaVerías un 404, porque el servidor sí responde pero no encuentra el archivo con esa ruta exacta. El fallo no es del servidor: está en que el HTML apunta a una ruta que ya no es correcta.

Actividades en el ordenador

Como en la sesión 3, esta parte se hace en el ordenador, con las DevTools abiertas en la pestaña Network. Puedes usar tu propia web personal o cualquier página real (por ejemplo, la del propio instituto).

Actividad 1 — Descompón una URL real

  1. Abre cualquier página en el navegador y abre las DevTools en la pestaña Network (clic derecho → Inspeccionar → Network).
  2. Recarga la página con F5.
  3. Busca en la lista la primera fila, la del propio documento (tipo "document"), y haz clic en ella para ver su URL completa.

Comprobación observable: se abre un panel de detalle con la URL completa de esa petición, y puedes ver su código de estado (normalmente 200).

En tu cuaderno, copia esa URL y separa a mano sus partes: protocolo, dominio, ruta (y parámetros o fragmento, si los tiene).

Actividad 2 — Encuentra una URL con parámetros

  1. Con la pestaña Network todavía abierta, ve a un buscador (por ejemplo, el buscador interno de una tienda online o de una web de noticias) y busca algo.
  2. Mira la barra de direcciones o la nueva fila que aparece en Network: busca el símbolo ?.

Comprobación observable: aparece una URL con uno o varios pares clave=valor después de ?, relacionados con lo que has buscado.

🤔 Antes de seguir: ¿por qué crees que muchos buscadores usan parámetros en la URL en vez de, por ejemplo, tener una página distinta para cada búsqueda posible?
Ver respuestaPorque sería imposible crear de antemano una página para cada búsqueda que alguien pudiera escribir. Con parámetros, una sola página sabe leer lo que le llega en la URL y adaptar el contenido a partir de ahí.

Actividad 3 — Busca un código de estado distinto de 200

  1. Con Network abierto, escribe a propósito una dirección que no existe en un sitio real que conozcas (por ejemplo, añadiendo /estoNoExiste al final de un dominio).
  2. Mira la fila del documento en Network.

Comprobación observable: el código de estado de esa fila ya no es 200 — normalmente 404.

¿Dónde miro esto? Cada vez que algo "no carga" en una web (tuya o ajena), la columna de estado en Network es lo primero que hay que mirar: te dice si el problema es que no se encuentra el recurso (4xx) o que ha fallado el propio servidor (5xx).
